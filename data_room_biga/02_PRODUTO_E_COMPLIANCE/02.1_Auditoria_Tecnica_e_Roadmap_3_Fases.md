### Gargalos para 100 corretores simultâneos
| # | Gargalo | Impacto | Correção |
|---|---|---|---|
| 1 | 1 processo Node + sessão Baileys por corretor (`deploy/corretores.sh`) | 100 × ~250 MB ≈ 25 GB RAM; VM grátis tem 24 GB | Workers multi-sessão (10–20 sessões/processo) + fila |
| 2 | Persistência em JSON reescrito inteiro (`store.js`) | I/O cresce com o arquivo; sem consulta entre corretores | Postgres (seção 3) |
| 3 | Gemini chamado em todo pedido, sem cache nem teto | Cota/429 e custo linear | Chamar só quando `localNaoReconhecido`; cache por hash do texto (pedidos repetidos em vários grupos) |
| 4 | Apify sem teto por plano | Destrói margem | Cota mensal por plano + cache de resultados por critério (24 h) |
| 5 | Baileys (não-oficial) | Risco de banimento de número | Ritmo humano já existe; adicionar teto de envios/h por número e plano de migração para Cloud API |
| 6 | Mesmo pedido lido por N corretores do mesmo grupo | Processamento duplicado ×N | Dedup global por `hash(grupo+texto)`: parse 1×, match por corretor |

## 3. Arquitetura de dados: Fase 1 → 2 → 3

Postgres + PostGIS, multi-tenant com `tenant_id` e Row-Level Security. Fluxo por eventos: **captura → normaliza → deduplica → casa → mede mérito**.

```
mensagens_grupo ──parse──► pedidos (demanda) ──match──► matches ──► envios
       │                                                   │
       └──parse──► anuncios (oferta) ──dedup──► imoveis ◄──┘
                                              │   └─► condominios (PostGIS + 3D)
                       eventos_merito ◄───────┴── parcerias ──► ranking_mensal
```

| Tabela | Campos-chave | Fase |
|---|---|---|
| `tenants` / `corretores` | id, plano, creci, imobiliaria_id | 1 |
| `grupos` | id, wa_jid, nome, tenant_id | 1 |
| `mensagens_grupo` | hash (único), grupo_id, autor_hash, texto, ts, **expira_em** (90 d) | 1 |
| `pedidos` | id, mensagem_id, tipo, negociacao, bairros[], condominio_id, preco_min/max, quartos, status | 1 |
| `anuncios` | id, mensagem_id, corretor_origem, tipo, preco, area, condominio_id, fingerprint | 1 |
| `imoveis` | id, tenant_id, fonte (`carteira`/`grupo`/`portal`), fingerprint, geom (POINT), condominio_id, ativo | 1 |
| `matches` | pedido_id, imovel_id, score, decisao (ENVIAR/AVISAR/SILÊNCIO) | 1 |
| `envios` | match_id, canal, ts, resposta | 1 |
| `eventos_merito` | corretor_id, tipo (resposta_rapida, imovel_compartilhado, visita, venda_parceria), pontos, ts | 2 |
| `parcerias` | corretor_captador, corretor_vendedor, imovel_id, split %, status | 2 |
| `ranking_mensal` | corretor_id, mes, pontos, posição (view materializada) | 2 |
| `condominios` | id, nome, aliases[], geom (POLYGON), lotes, asset_3d_url, tour_url | 3 |

**Regras de alimentação automática**
1. Cada `anuncio` com `condominio_id` vira/atualiza `imoveis` (dedup por `fingerprint = tipo+condominio+area±5%+preço±5%`).
2. Cada envio, resposta e parceria gera `eventos_merito` → ranking (Fase 2) sem trabalho manual.
3. `condominios` já nasce na Fase 1 a partir do gazetteer; a Fase 3 só acrescenta `geom` detalhada e `asset_3d_url`. O estoque do mapa 3D = `imoveis WHERE condominio_id = X AND ativo`.
4. LGPD: `autor_hash` em vez de telefone em claro nas tabelas compartilhadas; telefone só no tenant controlador; `expira_em` com job de expurgo.
